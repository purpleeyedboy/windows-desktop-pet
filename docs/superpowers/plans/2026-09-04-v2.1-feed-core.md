# V2.1 FEED-CORE Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use test-driven-development and verification-before-completion to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build an isolated, auditable file-feeding transaction core that moves one explicitly dropped, validated Windows file to the Recycle Bin and commits reward/animation signals at most once.

**Architecture:** A pure transaction coordinator depends on injected validator, confirmation, recycle, reward, and animation ports. A versioned atomic JSON journal drives crash recovery; the Windows adapter alone owns COM/IFileOperation on a dedicated STA worker. A non-owning Drop-event adapter is the temporary DRAG seam, and an idempotent reward fake is the temporary HUNGER seam.

**Tech Stack:** Python 3.11, ctypes Windows COM, tkinter confirmation, JSON journal, pytest, PyInstaller, PowerShell, GitHub Actions.

## Global Constraints

- Do not alter approved art, motion, tilt behavior, golden images, or legacy visual tests.
- Accept only an explicitly dropped local regular file; reject directories, roots, links/reparse points, the program, repository/assets, system, and protected paths.
- Every operation requires a visible per-file confirmation stating “移入回收站”; cancellation, close, or failed validation performs no operation.
- Recycle only through Windows IFileOperation on a dedicated STA thread, with undo enabled and no permanent-delete fallback.
- Recovery is idempotent and uncertain outcomes become NeedsReview with retained audit data.
- Reward and animation occur only after proven recycle success and at most once per transaction.
- Automated tests use mocks and test-owned temporary directories only; real IFileOperation E2E is explicit opt-in.
- Logs and journals do not store contents or full sensitive paths.
